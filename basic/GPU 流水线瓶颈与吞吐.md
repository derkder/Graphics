# GPU 流水线瓶颈与吞吐

> 瓶颈是 `max(A, LS, V, T)`，不是四者相加。单个 warp 内部是串行的，但整个 core 的吞吐由最忙的那条流水线决定。

**可交互模拟器 → [在线打开](https://derkder.github.io/Graphics/assets/gpu-pipeline.html)**（浏览器打开，拖滑块看瓶颈实时切换）

## 有几条流水线

malioc 报几列取决于架构：

| 架构 | 典型 GPU | 流水线 | 条数 |
|---|---|---|---|
| Midgard | Mali-T760 / T880 | A、LS、T | 3 |
| Bifrost | Mali-G71 / G72 / G76 | A、LS、**V**、T | 4 |
| Valhall | Mali-G77 / G78 / G710 及以后 | **FMA、CVT、SFU**、LS、V、T | 6 |

- **A** 算术。Valhall 起拆成 **FMA**（乘加，绝大部分数学）、**CVT**（类型转换/打包）、**SFU**（sin/cos/exp/rsqrt/pow）
- **LS** 读写，访问内存 / buffer / UBO
- **V** varying 插值，UV、法线、顶点色从三角形三顶点插出来。Bifrost 起独立成一条
- **T** 纹理采样

条数不影响结论，多一条只是多一台并排干活的机器、多一个候选瓶颈。

## 为什么是 max 不是相加

关键在于**算的是延迟，卖的是吞吐**。屏幕上几百万个片元，帧时间由每秒吐出多少个决定。

假设每个 warp 需要 A 4 拍、LS 2 拍、T 1 拍。只有 1 个 warp 时总共约 7 拍，这时确实是相加。但 core 里同时驻留几十个 warp，几条流水线像几个工位，同时服务不同的 warp：

```
时间 →      0    4    8    12   16
A 单元:    [w1 ][w2 ][w3 ][w4 ]   ← 满载，4 拍/warp
LS 单元:    .[w1].[w2].[w3].[w4]  ← 一半时间闲着
T 单元:     ..[w1]..[w2]..[w3]    ← 更闲
```

稳态下 A 每 4 拍放行一个 warp，其余永远在等米下锅：

```
总时间 = 灌满流水线的开销（≈ 一个 warp 的串行延迟，常数） + N × max(A, LS, V, T)
```

**"相加"没有消失**，它藏在第一个 warp 走完全程的灌注开销里。但 N 是几百万，常数被摊掉。这跟"流水线产能等于最慢工位"是同一个定理，在模型内部是精确的，不是近似。

> 洗衣店：洗衣机 40 分钟、烘干机 20 分钟、熨烫台 10 分钟。一件衣服进店到取走 70 分钟，但只要衣服不断，每 40 分钟就出一件。多买熨烫台没用；换台快一倍的洗衣机，产能翻倍。malioc 标 `A bound` 就是说 A 是那台洗衣机。

## A 依赖 T 的结果怎么办

真实 shader 里 A 几乎总是依赖 T。但——

> **依赖卡住的是 warp，不是机器。**

采样指令一发出去，T 机器立刻就空了（模拟器里那条虚线：warp 在等，机器没在等）。warp 挂起期间调度器转头服务别的 warp，A 单元照样满负荷，只是干的是别人的活。

所以依赖增加的是**单个 warp 的延迟**，不是**单元的占用率**，而吞吐只跟占用率有关。模拟器里"把采样提前发"开关（编译器把不依赖采样结果的指令搬进等待窗口）的实测：

| 场景 | 单 warp 延迟 | 总时间 |
|---|---|---|
| 驻留 8 个 warp | 15 → 13 拍（−13%） | 51 → 49 拍（**−4%**） |
| 驻留 2 个 warp | 15 → 13 拍（−13%） | 79 → 69 拍（**−13%**） |

**依赖真正伤到你的场合只有一个：occupancy 不足。** 这也是优化手册总说"提前采样 + 减少寄存器占用"的原因——前者缩短依赖链，后者提高能驻留的 warp 数，都是在保证流水线不断粮。

> GPU 靠 TLP（线程级并行）活着，不靠 ILP（指令级并行）。单个 warp 内部依赖成一条直链都没关系，只要排队的 warp 够多，几台机器就都不会闲。

## Occupancy

能同时驻留多少 warp，是 GPU 唯一的延迟隐藏机制。

```
饱和所需的 warp 数 ≈ ⌈单 warp 延迟 ÷ max(各流水线)⌉
```

低于这个值瓶颈单元就空转，实测从 `N × max` 向 `N × 相加` 退化。压低 occupancy 的主要是**寄存器用得凶**（寄存器堆固定，每个 warp 占得多能驻留的就少），其次是片元太少的小 draw。

坑：一个寄存器爆炸的 shader 不光自己慢，还拖累同期混跑在这个 core 里其它 warp——因为 core 里驻留的 warp 可以来自不同 shader、不同 draw call，甚至顶点和片元混跑，共享同一个寄存器堆和驻留名额。

## 坑 / 什么时候不成立

公式在模型内精确，但"真机 = 这个模型"是近似：

1. **warp 不够多** → 瓶颈单元空转，滑向相加那端
2. **cache 没命中** → malioc 的 LS/T 拍数按理想缓存给，真机 miss 会让这两格暴涨，静态显示 A bound 的可能实际是带宽 bound
3. **各流水线并非零干涉** → LS 和 T 共享 L2 与总线带宽，寄存器堆端口、发射宽度也有限
4. **流水线之外还有墙** → tile 写回、blending、render pass 排空、顶点与片元阶段衔接

## 实操含义

**`N × max` 是性能下界（最好情况）**，真机只会 ≥ 它。

- malioc 标的 bound unit 说明"就算一切理想，极限也卡在这台机器上"，据此决定该削哪类指令是可靠的
- 削减非瓶颈单元的指令数，对帧时间几乎没影响
- SFU 在 Valhall 被单拆出来，意味着 `pow/exp/sin` 不再和普通乘加抢机器。FMA 瓶颈而 SFU 空闲时，改写成超越函数形式反而可能更快（Midgard 时代不成立）
- 但两个 shader 静态数字接近时谁更快、优化后到底提多少帧，**必须真机测**——偏差来自静态工具看不见的 occupancy、cache、带宽
